### Defects from the second-pass evaluation (2026-09-01)

Three bugs in shipped behaviour, found by three independent evaluators and verified in the code. Sequenced ahead of every PRD in `docs/prds/`. See `docs/prds/INDEX.md`.

- [x] **C-050** — *(defect D1)* The tap that meant one thing and did another — `applyTransition`'s `unexpected_target` refusal has existed since C-004 for exactly the stale-screen double-tap, and neither real caller passed a `to`, so it could never fire from a screen. Two screens on one board plus a five-second poll made "Start cooking" mark an order picked up. Both directions fixed, not just the forward one: `advanceOrder(orderId, to)` and `revertOrder(orderId, reason, to)` take the status the card was drawn against, guarded as untrusted input by one `readTarget`. C-047's lesson word for word — the engine was right and the screen never asked. The regression test was verified by reverting the fix and watching it fail. No migration.
- [x] **C-051** — *(defect D2)* The sales report never reads `paymentState`, so revenue counts food nobody paid for — C-016's "charged, not collected" defence stopped holding at C-038/C-048, and the caveat list went on describing the behaviour accurately while its premise expired underneath it. Net sales keeps counting uncollected food (2026-09-01 decision #1: cash-basis would restate every past headline to fix a gap a second number states directly); `SalesReport` gains a `PaymentSplit` of `collected` / `outstanding` / `refunded` that sums to revenue and never nets, plus the chase list — day, number, name, amount — because a count of six is not something anyone can act on. `loadReportOrders` selects `paymentState`, `seq` and `customerName` for the first time, and the file's "no names here" header is corrected rather than falsified. Scoped to exactly the orders revenue covers: the till is out of scope by decision #2. No migration.
- [x] **C-052** — *(defect D3)* The placement replay accepts any non-empty idempotency key and returns a full `ORDER_RECEIPT` including `statusToken`. Not a live break — the browser uses `crypto.randomUUID()` — but no entropy was enforced on a key that doubles as a read handle for a secret, and the seed and rush scripts wrote `seed-order-0` into a table the deployed demo still holds. `isIdempotencyKey` (canonical UUID, version 1-8, RFC variant checked so 36 characters of zeroes cannot pass) called once at the action boundary, with its own `idempotency_key_invalid` kind — the one refusal aimed at a programmer, and until C-084 the kind is the only name it has. Scripts keep deterministic keys via `derivedIdempotencyKey`, name-based like a UUIDv5 with the version nibble truthfully `5`. The check stays at the boundary and not in `placeOrder`: the action is the only caller behind a request, and pushing it down would have converted 21 trusted call sites for no boundary not already covered. A format check is a floor, not a proof — the real fix, binding the replay to the placing session, is PRD 6 E-1. No migration.

### PRD 3 — money that reconciles

- [x] **C-064** — *(PRD 3 P0-2)* A balance, not a boolean — `paymentState` cannot say "$31.20 of $34.20", which is the answer the moment anything is partial. `orderBalance` in `packages/core`, integer cents, both figures clamped at zero for two different reasons (we never hold a negative amount; an overpayment is money owed to the customer, and a negative debt invites collecting it twice). `canCollectPayment` rewritten to take an AMOUNT rather than the enum — a number, not the balance object, so the status module stays uncoupled from the payment stream. All three readers converted, which was the point: the queue's unpaid badge, the staff receipt, the report's outstanding list. The PRD's acceptance case passes to the cent, and a db test proves the counter collects the REMAINDER rather than re-charging the ticket. One deliberate change: a refunded order now reads as outstanding instead of falling out of the split — the customer has the food and we hold nothing — which also makes `collected + outstanding` exactly the revenue booked, an invariant the enum could not hold. No migration.
- [x] **C-063** — *(PRD 3 P0-1)* The event stream becomes the truth about money — the PRD's own text said "a human has to pick; the whole PRD's data model forks here", and it was asked and answered: **decision 5**, the event stream is the truth and `Order.paymentState` becomes a derived cache that stays indexed and stays the read every surface already uses. **Decision 6** in the same pass: a comp is a record, not a charge, so P0-3 does not breach the master PRD's Non-Goal. `OrderEvent.amountCents` and `providerRef` as columns rather than JSON keys, because a balance summed out of JSON is one no index can help and no constraint can defend; a CHECK written as an equivalence so money events must carry an amount and nothing else may (`total_mismatch` deliberately on the "must not" side — it holds amounts and moves none); and a second CHECK making direction the kind, never the sign. `derivePaymentState` in `packages/core`, proved against the column for every order in the seeded rush. Cost one discovery: **you cannot backfill an append-only table** — the C-003 trigger refused the migration's UPDATE by name, and it is disabled by name for the backfill and re-enabled unconditionally, because a lossless re-encoding of a fact already on the row is not the history-rewriting the trigger exists to stop.

- [x] **C-065** — *(PRD 3 P0-3)* Making it right — the operator's complaint word for word: there is no way to. Cooked food cannot be cancelled (correctly — the state machine goes on refusing, P0-5 is unchanged), so the counter comped **off-system** and the till and the report disagreed by an amount nobody wrote down. `adjustment`, a sixth `OrderEventKind`, appended beside the snapshot and **never** subtracted from it — decision 6 of 2026-09-01 in the schema comment: a record of a decision, not a charge, so the "no real payment processing" Non-Goal is untouched. Two migrations and not by preference: `ALTER TYPE … ADD VALUE` cannot be USED in the transaction that adds it, so the CHECK naming it is the next file — and C-063 having written that CHECK as an *equivalence* made it one line. Two kinds, `comp` and `partial`; `remake` is deliberately absent because it carries a link and a kind with no link is a word on a screen (C-066). **The bound is cumulative**, which is the defect the requirement's own wording hides: "larger than the order total" read as a single-amount check lets two $10 comps land on a $13.75 order, so `adjustableRemainingCents` is its own function with two readers — the validator and the screen. **A comp takes no amount from the client at all**: it is defined as the whole order, so the server derives it, which is strictly stronger than validating a number it did not need. Refused, never clamped, and the refusal names the bound. `paymentTotals` gains a third direction and `orderBalance` subtracts it from what is OWED rather than from what was collected — those are two different sentences, and `derivePaymentState` deliberately ignores adjustments so the cache goes on agreeing with the column. Every money surface followed for free, because C-064 had already made them all read one function: the queue badge, the receipt, the report's outstanding list. The customer's status page says an order was adjusted and structurally cannot say why — one number, no preset, no note, no name. Cost one honest correction to C-064's own entry: `collected + outstanding` is no longer exactly the revenue booked once an order is comped, which is correct rather than broken. Two hand-written migrations, no backfill — an order comped before today was comped on paper.

- [x] **C-066** — *(PRD 3 P0-3, the rest)* The remake link — Ivy is back at 6:52 with a torta she ordered with onions OFF and a note saying "cut it in half please", and got neither. **Decision 7 of 2026-09-02** settled the PRD's own Builder question ("the kitchen needs a ticket; the report needs a link"): a remake is a **real second order**. The two needs do not pull evenly — either shape gives the report its number, and only this one gives the kitchen something to cook. New `(businessDay, seq)`, real ticket, ages and advances, lines **copied from the original's snapshot** rather than re-priced (Ivy's negation and her note are the point; a remake that loses either goes out wrong twice, and a menu repriced since 6:00pm must not change what a 6:52pm remake is worth). Comped in full at creation, so no counter is ever shown "$13.75 due" for food nobody will be charged for — reusing C-065 rather than inventing a second zero-money concept. **The report exclusion is load-bearing, not a nicety**: left alone the remake is `sold` by every rule the report applies, and would book a second sale, double the top-item units, and record an onions attach on the remake of an order that said NO onions — the exact fiction this PRD opens with. `remakes` is its own number on `/kitchen/report` with copy saying why it is not in the totals above. One migration, one file (nothing *uses* the new enum value, so C-065's two-file rule does not apply, and no CHECK changes because a remake carries no amount). **The seq-retry loop was extracted rather than copied** — one loop, two callers, because a second hand-written copy of the constraint-contention mechanism is the obvious place to get it subtly wrong. Its own form and section on the receipt, for two reasons that both bite: a remake must survive an order already comped (the PRD's own scenario is money back AND a new torta), and a shared form's implicit submission would make Enter in a note field mint a kitchen ticket. Cost one real defect found by its own test: a concurrent double-tap **threw** instead of replaying, because the extracted loop's recovery handler was not passed on the remake path.

### PRD 7 — loyalty

**Decision 8 of 2026-09-02: the master PRD's loyalty Non-Goal is LIFTED, by the
owner.** `prd-loyalty.md`'s own recommendation was to shelve it; that was read
and overruled. What survives of the Non-Goal is a boundary — one integer per
member, and a second entitlement dimension is where the objection it encoded
genuinely begins. Decisions 9 and 10 set the numbers.

- [x] **C-100** — *(PRD 7 P0-1 schema, P0-2)* The ledger — `LoyaltyMember`, `LoyaltyEvent`, the kind enum, five settings columns, and the pure balance function. **The phone is never stored**: `phoneDigest` is an HMAC under a pepper held in the ENVIRONMENT, not the database, so a dump of these tables is not a customer list — and the pepper is an env secret where `StaffMember`'s PIN salt is a constant, because a ten-digit phone number has a small enough keyspace that an unpeppered digest is decorative. Four CHECKs and a trigger, each one a mechanism the application is then allowed to be careless about: the sign tied to the kind as a single `CASE` **with `ELSE false`** (so a fifth kind cannot ship without editing the expression — without the `ELSE` the unmatched kind is NULL and a CHECK passes on NULL, which is a guard that reads as enforced and is not), money non-null exactly on `redeem`, a non-negative reward value, a four-digit `phoneLast4` (a partial write leaving it short is a counter lookup that matches everybody), and **the partial unique index on `(orderId) WHERE kind = 'earn'` — P0-3's whole mechanism, landed here rather than with the earn that uses it**, because the state machine permits reverts and `ready → picked_up` can happen twice on one order. **`points` is SIGNED, unlike `OrderEvent.amountCents`, and the asymmetry is deliberate**: a ledger's direction is its sign because the balance is a plain sum, while money's direction must be its KIND because a balance trusting a sign could not tell a refund from a negative payment. The append-only trigger blocks UPDATE and **deliberately permits DELETE**, because P0-5's forget is a real delete and the member Cascade is how it reaches these rows — blocking it would make "forget this customer" either impossible or a lie. Two Cascades-and-Restricts asymmetry: a member's ledger dies with the member, an order and a staff member outlive every row pointing at them. `loyaltyEnabled` defaults **false** and that is load-bearing, not a safe default. The `loyaltyExpiryDays <= retentionDays` CHECK P0-5 requires is **not** here — `retentionDays` first exists in C-091, and half a constraint reads as enforced and is not. One hand-written migration.

- [x] **C-101** — *(PRD 7 P0-1)* Enrolment — a member is a phone number and nothing else, and the phone is still never stored. `normalizePhone` in `packages/core` is the one function three call sites ask (the checkbox's enable rule, the enrolment write, the counter lookup), which is what makes `(555) 010-2233` and `5550102233` **one** member rather than two — a duplicate member has no symptom, so the constraint that prevents it has to be a shared function and not three regexes. `packages/db/loyalty.ts` holds the HMAC under `LOYALTY_PHONE_PEPPER`, the upsert, and `memberByPhone`, which hashes the typed number so **the plaintext never reaches a `where`** — a `contains` on a phone column is the query that turns a loyalty program into a searchable customer index. **An unset pepper refuses by name and never hashes under an empty key**: an empty-key HMAC is perfectly stable, so it would enrol members happily and orphan every one of them the day the pepper is configured — `phoneDigest` throws, `enrolMember` returns `loyalty_pepper_unset`, and the screen does not render the checkbox, because `offered` is `loyaltyEnabled && hasLoyaltyPepper()` as one expression the screen and the writer both read. The checkbox is unticked by default, disabled until the phone is one a membership can be keyed on, and says what is kept and for how long; with the program off it does not exist to be read by a screen reader either, and the whole customer flow is what it was. **Enrolment happens after the order is written and cannot fail it** — a punch card that could not be written must not cost a customer their food — so every outcome, a throw included, becomes one word from a closed set on the placement log line. The upsert's `update: {}` is deliberate: a returning customer keeps the name and the instant they enrolled under, because that instant is what expiry and retention are both counted from. NANP-only is a recorded `ponytail:` ceiling, not an oversight. No migration — C-100 landed the schema.

- [x] **C-102** — *(PRD 7 P0-3)* Earning at pickup — the punch card's first punch, and the item is mostly one decision defended twice. **The earn fires inside `applyOrderAction`'s transaction**, guarded by `salesRoleOf(decision.status) === 'sold'` and never by `=== 'picked_up'`, so a second sold status makes the compiler find this reader. **It is deliberately the opposite shape to C-101's enrolment, and the asymmetry is the point**: enrolment hangs off a placement and must never fail it, because a punch card that did not start must not cost a customer their food and there is a later moment to fix it; a `picked_up` that committed without its ledger row is a customer who paid, took the food and earned nothing, and the order is terminal — there is no later moment to retry from. So the earn commits with the status or not at all. **`skipDuplicates` — `ON CONFLICT DO NOTHING` — lands on C-100's partial unique index on `(orderId) WHERE kind = 'earn'`, and a check-then-write is banned for two reasons rather than one**: it is two cooks' taps away from a double earn, and a second insert that THREW inside the transition would roll back the ordinary revert-and-re-advance, taking the cook's tap down with it. The index swallows the duplicate and the re-advance succeeds. **`lastActivityAt` moves only when a row was actually written** — a re-advance that earned nothing must not restart the twelve-month expiry clock, because a fat finger silently extending how long a named person's data is held is exactly what P0-5 exists to bound. Points are `floor(subtotalCents / 100) × pointsPerDollar` off the frozen snapshot: $14.95 earns 14, tax earns nothing, and a menu repriced under a placed order changes neither. Under a dollar writes **nothing** rather than a zero-point row, which would fail C-100's sign CHECK and roll back the pickup. A revert claws nothing back — recorded ceiling, `adjust` is the correction. No migration; C-100 landed the mechanism this item is built on.

- [x] **C-103** — *(PRD 7 P0-1's reader)* The counter panel — a balance had existed since C-102 and nothing rendered it. On the staff receipt: the member behind the order, by name and last four, with the points and whether a reward is available. **`memberByPhone` on the ORDER's own phone, not a search box** — the panel answers "who is this order's customer and what do they have", which is what a counter asks with the food in its hand; a phone-lookup control would be a second entry point into a customer index, and not building one is the thing this program has been careful about since C-100. Guarded by `gateState.loyalty.offered`, so with the program off the lookup is not attempted and there is no copy to be read by a screen reader either. `hasReward` and `pointsToNextReward` decide which line renders, which are **the same functions C-104's control will ask**, so the screen that offers a reward and the write that spends it cannot disagree about what one is. **Read-only, and a spec asserts there is no reward button** — spending is C-104's, and a control that looks live and is not is worse than none. Also closes the gap C-101 and C-102 both recorded: `enrolled` on `OrderConfirmation` and one line on the checkout receipt, **a boolean rather than the refusal word** (the six outcomes are for the operator's log; "we could not key a membership on that number" is not a sentence for a customer's receipt) and **carrying no balance**, because points are earned at pickup and the honest number at checkout is zero. `adjustLoyaltyPoints` joins `backdateQueue` as a fixture that writes what the product would write: the threshold is 100 points and a burrito earns 10, so crossing it through the screens is ten orders of clicking to assert one line of copy. No migration.
- [x] **C-104** — *(PRD 7 P0-4)* Redeeming — the panel grew the control C-103 deliberately left off it. **Two rows in ONE transaction**: a `redeem` on the ledger and an `adjustment` on `OrderEvent`, because a redeem alone takes a customer's points and charges them anyway, and an adjustment alone gives ten dollars away for free. **No new money mechanism** — `adjustOrder` gained an optional transaction client so the money side goes through PRD 3's own validation rather than having the rule copied inside a second writer. **The order id is the only input**: the amount is the settings row's, the member is whoever enrolled under the order's own phone, and nothing about a reward arrives from a client. Bounded by what is **owed** (`orderBalance`), which is stricter than what is adjustable — an order collected in full owes nothing, and a reward against it would be cash handed back through a refund path that does not exist. **Refused, never clamped**, over an order owing less than the reward is worth, with NEITHER row written. `planRedemption` is asked by the screen and by the write, so a button that renders is a button that works. Hand-written migration: `LoyaltyEvent_one_redeem_per_order`, the partial-index sibling of C-100's earn index — an order legitimately carries both kinds at once, which is why neither can widen. **`loyalty_reward` is deliberately not in `ADJUSTMENT_REASONS`**: that array is a rendered dropdown AND a form action's guard, so adding to it would have shipped a free-ten-dollars option in the Make-it-right picker and widened the POST guard in one edit — split into `isStaffAdjustmentReason` and the wider engine union, and `tsc` found both readers. **The finding, from the e2e and not from reasoning: counter redemption is a PAY-AT-PICKUP feature.** The checkout defaults to "Pay now — card", so most orders reach the counter owing nothing and correctly offer no reward — a captured card charge cannot be handed back without C-067's refund, and applying the reward before the money is taken is P1-1, gated on SMS. Both halves are now asserted rather than discovered. **Left behind:** half a reward is not spendable, a spent reward has no undo (a staff `adjust` and a second adjustment are the correction), and the customer still pays tax on food the reward covered — P1-1's before-tax version is gated on SMS.

- [x] **C-105** — *(PRD 7 P0-5)* Expiry, and the forget — the last P0 of the loyalty PRD and the other half of the bargain decision 10 struck. **The CHECK C-091 held back**: `loyalty_expiry_within_retention` (`loyaltyExpiryDays <= retentionDays`), hand-written, landing here rather than with the column because a constraint tying two settings together means nothing until a sweep acts on both. No second positive guard — `loyalty_settings_positive` already covers zero, and one constraint per claim. `expireInactiveBalances(now)` writes ONE `expire` row per stale member worth exactly minus the balance, against no order, so the ledger still explains itself; **it is idempotent without a constraint** (the second run finds zero and a zero-point row is skipped, unlike C-102's earn which needed an index because it races a cook's tap) and **it does not move `lastActivityAt`**, because expiring is done TO a member and moving the clock would reset the window that eventually deletes the row. **It ignores `loyaltyEnabled`, and that is the decision in this item** — every other write in the file checks the switch, and gating this one would make switching the program off make every outstanding balance immortal, which is the exact failure P0-5 exists to prevent; there is a test that expires a balance in a restaurant with the program off. The forget path grew a real **DELETE**: the member and, through the Cascade, its whole ledger — two verbs on two tables in one operation, and the asymmetry is PRD 7's entire argument (an order is a snapshot of a sale and survives; a member is nothing but who somebody is). **`forgetMemberByPhone` runs BEFORE the scrub**, because the phone is the only key into the member table and `forgetOrders` nulls it — the second time ordering inside that file is load-bearing. **The sweep selects members on `lastActivityAt`, never on the orders it just scrubbed**: a customer with one 400-day-old order and one from last week has that order forgotten and a live punch card, and the CHECK is what makes the two passes order-independent. `retentionCutoff` became `cutoffDaysBefore` — two windows, one subtraction. P0-5's acceptance test is an order with an earn, an adjust and a redemption: member and ledger gone, the `adjustment` on `OrderEvent` intact with its amount and its staff member, and the whole sales report byte-identical. **Found from the tests: adding a CHECK moved another test's error message** — a zero retention window now violates the new constraint as well as `retention_days_positive`, so a test about retention failed citing loyalty; asserting a refusal by name only works where exactly one constraint can produce it. **Left behind:** nothing schedules any of the three passes, expiry is neither attributable nor announced, a balance expires all at once rather than per earn, and shrinking the window has no dry run — which is why C-106 cannot add a control for it without adding one.

- [x] **C-106** — *(PRD 7 P1-2, and P0-6)* The program's own screen — `/kitchen/loyalty`, the last item of the loyalty PRD below the SMS line. **The liability is TWO numbers and the gap between them is the requirement**: every outstanding point at the reward rate (`accruedCents`), and the whole rewards that could be spent tomorrow (`redeemableCents`) — different amounts because C-104 refuses half a reward rather than clamping it, and an owner shown only the first over-provisions while one shown only the second is surprised the week everybody crosses the threshold. `loyaltyLiability` takes BALANCES, not a sum, because the whole-reward division and the negative-balance floor are both per-member questions a pre-summed total cannot answer — **a negative balance is not a negative liability**, so one fat-fingered staff `adjust` cannot quietly cancel out somebody else's real points. **Three aggregates, never a `findMany`**: a count, a `groupBy(memberId)` for the balances and a `groupBy(kind)` for the window, and **members are counted separately from the balance grouping** because a customer who enrolled and never came back has no ledger rows — they are a member with nothing, not a missing member. The liability is all-time while everything else is the window, which is the only reading either can have. The redemption rate is points spent over points issued, **null rather than zero** when nothing was issued, and **allowed above 100%** with the copy that says why: a punch card is savings, so points earned before the window get spent inside it. **The switch shipped and the numbers deliberately did not** — `loyaltyEnabled` is a button, while the reward terms and both windows render read-only with their reason, the same shape the settings screen gives the timezone and the tax rate: changing `rewardValueCents` restates the liability of every point already earned, raising `rewardThresholdPoints` takes a reward off somebody who has one, and shrinking `loyaltyExpiryDays` destroys balances with no preview — **C-105's dry-run condition is satisfied by not shipping the control**, which is the other way to satisfy it and the one this item took. P0-6's static check reads the report loader AND the report page as TEXT and fails on the word, plus a schema check that `model Order` carries exactly one loyalty line and it is the back-relation — **a runtime test cannot tell "the report reads no loyalty table" from "it read one and it was empty"**, which is why a requirement about what code *cannot* do is asserted against the code. Verified against a deliberately broken copy before being trusted. `Stat` and `Section` moved out of the report page into `apps/web/lib/panels.tsx` the moment a second screen wanted them. **`setLoyaltyEnabled`'s e2e fixture stays a direct write and now has a spec behind it** — one test drives the real button and checks the checkout follows, so the ten specs that use the shortcut are not resting on an unchecked claim. No migration. **Left behind:** no dry run and therefore no window controls, nothing warns a member before expiry, the liability is not broken down by age, and the screen has no export.

### PRD 1 — the report someone acts on

Ranked #1 in `docs/prds/INDEX.md` — the only theme all three evaluators raised
independently. Its defect item shipped early as C-051 (D2); the PRD's own
Phasing section was drafted before that and has been renumbered to match this

- [x] **C-053** — *(PRD 1 P0-1)* Net sales, tax, and gross are three different numbers — the screen has had the right figures since C-016 and the wrong word over one of them ever since: the headline was `Σ totalCents` labelled **Revenue**, so a month end books the state's sales tax as the shop's earnings and understates the tax line by exactly the same amount. Three tiles — **Net sales** (the only one of the three that is the shop's money), **Tax collected**, **Gross** — and the word deleted from the page rather than moved to another tile, which is the version of this fix that leaves the same sentence readable to an accountant. **`SalesReport.totals` is summed off the day buckets, not off a fourth accumulator**, so the headline and the By-day table are arithmetically incapable of disagreeing. `HourBucket` gains the two money columns By-day already had; By-hour keeps its bar and states the three numbers in the row, because a second table of the same rows would be two renderings of one fact. **The reconciliation is asserted, not rendered** — `net + tax = gross` on every day row, every hour row and the window, over a fixture whose 90¢ on $10.95 is 8.219% and divides into nothing, so an implementation that recomputed tax from a rate instead of reading the snapshot lands a cent away and fails. **Found: Top sellers called `lineTotalCents` "Revenue" too** — accurate arithmetic under an inaccurate word, one table down, and it would have survived a fix that only touched the tile. Nothing on this path reads `RestaurantSettings.taxRate`, structurally: the page loads settings for the timezone alone. No migration. **Left behind:** the rolling windows still bucket on an instant (P0-3 is next), tax is one number per order with no categories, and there is no comparison against the last period.

- [x] **C-054** — *(PRD 1 P0-3)* Today — the report has had four windows since C-016 and every one is a multiple of 24 hours counted back from `now`, so the question the screen is actually opened with mid-service — *how did today go* — was answered by "the last 24 hours", which at 2pm is half of today plus half of yesterday. **The window is a string match, not an instant range**: `businessDayOf(now, timezone)` compared against the `businessDay` column, which the same `restaurantClock` reading wrote at placement — so the report's "today" and the counter's "#047 today" are one day by construction, and the local → instant conversion `business-day.ts` refuses to make (a DST boundary has two answers or none) is never needed. `ReportWindow` is `Date | { businessDay: string }` deliberately: the `Date` arm still means the instant bound, so all fifteen existing call sites read as they did and the behaviour change did not arrive inside fifteen mechanical edits. **One `where` fragment, three loaders** — sales, time-in-state and the quote grades are bounded together, because a page showing today's sales beside a week of time-in-state is a page that is lying about one of them. The partial-oldest-day disclaimer is **suppressed rather than reworded**: a business day is whole by definition, and a caveat under every window is one nobody reads, including the honest one. **The test's two orders share a UTC day and not a restaurant day** — both placed 2026-07-15 UTC, one of them the evening of the 14th in Los Angeles — so a UTC-day window and a 24-hour slice both fail it; verified by breaking it before trusting it. No migration. **Left behind:** `Today` is midnight-to-midnight restaurant time and inherits the service-day-offset caveat the order-number reset already carries; no `Yesterday` and no arbitrary day, which is P1-1's date range and should arrive as two inputs rather than a second special case.

- [x] **C-055** — *(PRD 1 P0-4)* The attach table leads with the decidable rows — a required modifier group is 100% by construction (every unit took a protein because the menu gave no choice), and the table was sorted by rate, so the screen led with a column of restatements of the menu while the row a decision turns on — *how many burritos paid the extra $2.50 for guacamole* — sat below all of them. **Ranked by attached volume in the engine, split in the page**: `salesReport` goes on returning every row, because a rate that is uninteresting to read is not a rate that is wrong and P1-2's CSV will want all of them; the screen shows the rates under 100% and folds the rest behind a closed `<details>` labelled "Always taken (required choices)". **Folded, not dropped** — "guacamole is at 100%" and "guacamole is required here" are one row read two ways, and the second reading is the only thing on the product that catches a group built required that was meant to be optional. **"Always taken" is inferred from the rate and NOT from `minSelect`**, deliberately: the honest version of that test is a menu join, on the one page whose entire discipline is that it never joins to a menu table — so a required group and an optional one everybody happened to take render identically, which is the correct trade for a report about what was ordered from a menu that may not exist any more. The snapshot-rule assertion P0-4 asks for is **C-016's byte-identical-after-mutation test passing unchanged**; an in-memory re-sort cannot introduce a join, and a second copy would assert the same thing twice. **Found: a closed `<details>` takes its rows out of the accessibility tree**, so the existing negation test's `getByRole('table')` stopped seeing the row it asserted on — a laxer version of that test would have gone green by finding nothing. Rewritten to match `td` cells by CSS across the whole section, hidden rows included, because "NO onions appears nowhere" has to mean nowhere. No migration, no new query. **Left behind:** a 100% row with a single sale folds away like a required group (a minimum-units floor would fix it and would be the first invisible threshold on the page), no column sort, and attach is counted over units rather than over orders.

- [x] **C-056** — *(PRD 1 P0-5)* p90, the ran-late count, and the slowest five — the time-in-state table has stated an average since C-020, and an average is the one summary that can be true of a service nobody had: twenty-four six-minute tickets and six half-hour ones average eleven minutes, and the six who waited half an hour were on no screen. **Two grains, deliberately kept apart** — the distribution columns are per STATE (how long is a ticket on the grill, which is what the tally has always measured) and the ran-late count and slowest list are per TICKET, placed → last `ready`, because that is the number a customer actually waited and no single state is. `p90Ms` and `worstMs` come from the per-order durations rather than from the total — **an average is derivable from a sum and a percentile is not** — over the same denominator the average already used: the orders that ENTERED the status, because padding the sample with zeros for orders that never got there reports a p90 of zero for a kitchen that is visibly behind, and there is a test that fails under exactly that implementation. **Nearest-rank, not interpolated**: an interpolated 28.4 names no ticket, a nearest-rank 31 names one somebody can go and look up. **The threshold is asked for, not restated** — `isOverdue` extracted out of `queueAging`, so "ran late" is literally the comparison the card's red state is, `>=` included, and the e2e proves the boundary end to end because the seeded Priya Shah took exactly fifteen minutes. **The new reader adds NO third status restatement**: the obvious shape was a second loader carrying `events: { some: { toStatus: 'ready' } }` — a third copy of a status in Prisma's dialect, on the path the systems review had already flagged for having two — so `loadStatusTimelines` widened to a `TicketTimeline` instead and the engine decides who reached ready by walking the log it already loads. The one remaining restatement is `loadQuoteSamples`, which has to filter in SQL (it is a filter, not a projection; lifting it means loading every order in the window to discard most of them), and it gets `isLeftOver`'s mitigation from C-039: a db test asserting the Prisma clause and `serviceTimes` select the same orders over a fixture holding a reverted ready and a cancelled order, matched on minutes ticket-for-ticket rather than on count. The slowest list stays capped at five against the requirement's own "all six appear", because the cap is a screen decision and the ran-late count is what says how many there were — asserted as `ranLate > slowest.length` so it cannot be misread. No migration, no new query.

- [x] **C-057** — *(PRD 1 P0-6)* Cancellations by reason — a cancelled order counts toward nothing else on the report, which is correct (nobody took the food, no money moved) and is exactly why the shop could not say what it cancelled: "we killed eleven tickets on Friday" was a fact held in a column on every one of those orders and never shown. Worse, the two things that happened most were on neither of the three buttons — **the customer changed their mind** and **the kitchen got it wrong** — so both went into `other` as free text, and the one bucket nobody can count was the one filling up. `CANCEL_REASONS` gains the two, **declared BEFORE `other` in the array AND in the migration**: `snapshot.test.ts` compares the engine's list against `pg_enum` position for position, so `ADD VALUE ... BEFORE 'other'` is not cosmetic, and appending at the end would also have put `other` in the middle of the cancel buttons on the one screen where it belongs last. **One migration file, not C-065's two** — the pair was needed because a CHECK *used* the new value in the same transaction, which is the only thing Postgres refuses; nothing names these, so a second empty file to look consistent would be cargo cult. **No backfill, and that is a requirement rather than an omission**: there is no `UPDATE` in the file and there must never be one, because reclassifying an order the staff cancelled under `other` invents history to make a new table look tidier. **Value is the ticket's gross and is deliberately NOT split into net and tax** against P0-1's own discipline — no tax is owed on a sale that did not happen, so the split is a distinction with nothing behind it. **The section renders OUTSIDE the "no orders were picked up" branch**: a window where everything was cancelled has no sales at all, and that is precisely the window somebody opens this table on. **The free text is a list under the table, not a column in it** — a count of `other` is the question and the sentences are the answer, and that list getting shorter is how you can tell whether this item worked. **`CANCEL_REASON_LABEL` moved rather than being copied**: there were already two renderings of a cancel reason (the queue's buttons, the customer's status page) and they are deliberately different wordings for different audiences, so a third staff-facing copy for the report was the obvious wrong move — the queue and the report share one `Record<CancelReason, string>` and the compiler asked for the two new words once. A null reason lands in `other` rather than being dropped: nothing writes one today, and a table whose counts do not add up to the number of orders cancelled is the failure mode nobody notices. The db test cancels through the real transition path, because `kitchen_error` is a value Postgres did not hold until this migration ran and no engine test can tell you whether it did. **Left behind:** a remade order later cancelled is counted as a remake and not as a cancellation (the remake `continue` runs first, deliberately, and that ordering is load-bearing); the notes list is uncapped; the reasons stay an enum and a migration, which is the PRD's own open question answered "not yet" for the reason it names; no by-day trend, which is the same shape as P1-3's; and a cancelled order's refund is a number on a different section of the same page with neither pointing at the other.

- [x] **C-058** — *(PRD 1 P1-1, P1-2)* A date range and a CSV — the last item of PRD 1, and the two halves are one session because they are the same query shape. The report has had five windows since C-054 and every one is a shape the CODE chose: today, or a multiple of 24 hours counted back from `now`. **"March" was not on the screen and could not be typed**, and the person who most needs March — the bookkeeper — does not want a screen at all. **`ReportWindow`'s object arm became a RANGE rather than gaining a third arm**: `{ businessDay }` is now `{ from, to }` and `Today` resolves to a range whose ends are equal, so there is ONE string-matching path below the type instead of two that have to be kept in step. **`businessDay >= from AND <= to` on a `Char(10)`** — no parsing, no local→instant conversion, the DST ambiguity `business-day.ts` refuses to resolve never arises; it works only because zero-padded `YYYY-MM-DD` makes lexicographic order calendar order, the same property `isLeftOver` leans on, and **the failure mode if that changed is not an error but a window silently holding the wrong days**. `businessDayRange` lives in `packages/core` because it is the one DECISION here and everything else is plumbing: **a backwards pair is SORTED, not refused** (two date inputs have no relationship between them, so typing the end first is ordinary, and the rendered label shows the range that was used), **half a range is `null`** rather than a narrower question, and **the month/day bounds are in the regex** because `2026-13-99` sorts above every real day of 2026 — a loose pattern does not fail, it quietly widens the window. **`report/window.ts` exists because this item creates the report's SECOND reader**: the screen and the export must bound the same days or the export is worse than nothing, so the whole answer moved — bounds, label, query string, filename slug — rather than the route re-deriving "which days" from the same params. **A plain GET form and two `<input type="date">`**: the browser already owns a picker, a calendar and the locale, it works with JavaScript off, and a bookmarked range is a working link. **A route handler, not a server action** — an action can only hand a string to a component, which then needs client JS, a Blob and a synthesised anchor click to become a download; `Content-Disposition` has done this since 1998, and being under `/kitchen` means `middleware.ts` guards it with the same one check every staff surface gets. **The CSV deliberately does NOT match the screen's strings**: `formatCents` renders `$1,234.56`, which arrives in a spreadsheet as text, and the column a bookkeeper opened the file to sum would not sum — plain decimals, the one place in the product where the screen's formatter is the wrong answer. By-day rows only and **no totals row** (a footer makes the file need re-parsing around it; a spreadsheet sums a column better than a file can). The db test asserts BOTH ends are real bounds — a `gte`-only window passes half of it — and the e2e types a range, checks the screen narrowed, then downloads the file and reconciles `net + tax = gross` on the row. No migration. **Left behind:** the export covers one of nine sections (the outstanding chase list is the right second FILE, not more columns on this one); no cap on the span, which is the same full scan every window here already is; the range and the rolling windows bucket differently and the screen now has two kinds of window where it had one; and P1-3's ran-late trend line is the last thing in PRD 1, the same shape as C-057's missing by-day cancellation trend, and they should arrive together.
