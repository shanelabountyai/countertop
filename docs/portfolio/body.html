No onions

Two words a phone order gets wrong often enough to build a product around. P0-11  the founding case

A removal that reads like an addition is a remake

Phone orders tie up staff during the rush and get transcribed wrong. The expensive version of wrong is a negation: someone asks for no onions, the ticket says onions, and the burrito comes back. Every design decision in this build points at that one failure.

So “no onions” is a real selection, not the absence of one. It is carried through the composer, into the order’s snapshot, onto the kitchen card — and it renders as a red block on a card where the additions are plain text. It is the only screen where getting this wrong costs money, and it is the one place the colour is loud.

C-017  the capstone

A rush that goes wrong on purpose

Thirty orders arrive in twenty minutes and the kitchen works them all the way through. A happy path replayed thirty times only proves the happy path thirty times, so five things go wrong every time it runs:

  • 86

    The kitchen runs out of guacamole at minute eight. One cart already holds it and is refused at the option grain — out of avocado is not out of burritos. One order already on the grill is cancelled with the reason attached. The orders already handed over do not move a cent.

  • undo

    A cook marks the wrong ticket ready. The undo appends a correction rather than erasing one, which is why the report afterwards still knows that ticket was on the grill twice — five minutes, then three.

  • no‑show

    Food nobody collects. Thirty-three minutes on the shelf, past all three marks, closed out as a no-show rather than a cancellation. They are different facts and the sales report keeps them apart.

  • ×2

    A customer taps Place order twice. One order exists, and both taps get the same order number back. Idempotency means the same answer, not merely no duplicate.

  • pause

    The restaurant pauses mid-service. Three arrivals are turned away with a reason rather than dropped. One comes back after it lifts, and their order is a new one, not a replay.

Order numbers run 1 to 30 with no gaps and no repeats, including the three submitted in the same instant. Nothing is stuck. And twenty minutes of service replays in under a second, because nothing in the ordering engine reads a clock — every price, every transition, every deadline is told what time it is. That discipline was for correctness; being able to run the rush as a test is the dividend.

P1-1  numbers that refuse to flatter

The report says what it does not know

The same screen, twice. On the left, mid-service: nothing has been picked up, so revenue is $0.00 and the no-show rate reads “—”, not “0%”. A rate over zero finished orders is unknown, and a screen printing “0% no-shows” on an empty day is lying — the kind of lie an owner acts on. The twenty-two orders still on the pass are counted as open rather than quietly missing from the totals.

On the right, after service. The time-in-state table is read off the append-only event log, not off the order — which is how it can count a reverted ticket’s two visits to Preparing separately. Its 4 h 3 min and 1 h 58 min are the same 243 and 118 minutes the rush’s tests hand-tally in a comment.

P0-1 / P0-2  the composer

The price on the screen is a preview, not a promise

Size is a required single-select modifier group with price deltas — not a separate “variant” concept. Required is min > 0, not a second flag that can contradict it. Intensity is none / light / regular / extra, and only extra can carry a surcharge. Every one of those is one mechanism instead of two, because two ways to say a thing are two ways to disagree.

The live total is display-only. The server re-prices every line when it enters the cart and again at placement; a client-supplied total is input to a mismatch log, never to the database.

P0-13 / C-023  the person running it

Guards where a valid number is the wrong number

$10.95 typed as $109.50 is a perfectly valid price, so no parser catches it. The only defence is showing the manager both numbers before publishing one — and then checking that the old one is still true when they tap Save. Two phones on one prep table is a normal Tuesday; the one who taps second finds out rather than quietly winning.

The same reasoning gave the opening hours a confirm step, listing only the days that move and warning separately about any the save would close. Timezone and tax rate are shown and deliberately not editable: changing either reaches backwards into every report already run and every order number already issued.

defects  eleven, each with how it was found

The two worth reading

The code that was never built

Every relative import inside the domain packages carried an explicit .js extension — the shape Node’s resolver wants, and TypeScript maps it back onto the .ts file beside it. Turbopack does not. The build failed with twenty-five copies of Module not found.

What made it hard was that the repo had been green for three sessions while this was true. Type-check: green. Lint: green. Every unit test importing those same modules through those same specifiers: green. None of them is a bundler. One server action had existed for two sessions and had never once been compiled, because a server action no rendered page imports is in no bundle. It surfaced three minutes into an end-to-end run, as a message naming a port.

The fix was a one-line-per-file deletion. The lesson took two occurrences: a build is a different kind of check from a type-check, and it now has its own gate step.

A demo where every alarm was always on

Stopping the seeded rush mid-service so the queue has live cards on it — a feature added deliberately — anchored the run a flat hour in the past. So a rush stopped twelve minutes in put the stop forty-eight minutes ago: every card past the fifteen-minute overdue mark, every aging flag lit. A lunch rush rendered as a disaster.

Nothing failed. The demo did exactly what it was told. It just showed a queue nobody would believe, and it passed every check because there was no check. An aging flag that is always on is worse than no aging flag — and the only thing that catches technically correct, obviously wrong is looking at it.

C-018 → C-031  after the backlog ended

A backlog that wrote itself

The plan ended at seventeen requirements and the project was complete against it. Fourteen more items followed, and all of them came from one place: the “Left behind” section every progress entry is required to carry — what was deliberately not done, recorded at the moment it was decided.

That turns out to be a better backlog than one written in advance, because every entry already knows why it was deferred. Half became features that had been database columns with no screen. The other half was the project auditing itself: constraints for rules only application code enforced, a gate step for the check that had escaped twice, shared test fixtures for a defect class that had recurred four times.

Four of the eleven recorded defects were found in those fourteen items — and three of the four were in code the earlier items had shipped green.
